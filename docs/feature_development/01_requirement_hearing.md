# ① 不明点の洗い出しと確認

> **この章でやること**
> ざっくりしたタスクから不明点を洗い出し、依頼元に確認して、
> 作るものを文章で固める。

---

## 発端

チケットにこう書かれています。

```
[タスク] ノートのNotion連携

作成したノートをNotionにも連携して
更新できるようにしたい。
Notion APIを使う。
```

**記載は以上です。** 仕様書はありません。

[要件定義書](../global_design/01_requirements.md) の「将来の拡張予定」に
挙がっていた項目が、実装対象として降りてきた状態です。

---

## Step 1. 不明点を洗い出す

### 手段が書いてあると、わかった気になる

```
「Notion APIか。ドキュメント読めば作れそうだな」
   ↓
作れるかどうかと、何を作るべきかは別の話
   ↓
「どのページに作るのか」が決まっていないことに、実装中に気づく
```

「Notion APIを使う」は**手段の指定**であって、仕様ではありません。

### 5つの観点で機械的に埋める

不明点を出せる人は勘がいいのではなく、**決まった観点で漏れなく確認している**だけです。

```
誰が   - 誰がこの操作をする？
いつ   - どのタイミングで動く？
何を   - 何のデータを送る？
どこへ - 送り先はどう決まる？
失敗   - エラー時どうなる？
```

今回のタスクに当てはめます。

```
【誰が】
・誰が連携を実行する？（作成者のみ / 管理者も / 誰でも）
・既存の編集権限と同じルールでよい？

【いつ】
・どのタイミングで送る？（公開時 / ボタン / 保存時）
・公開を取り消したら、ノートを削除したらNotion側はどうなる？
・連携後に編集したらNotion側も更新される？   ← 特に重要

【何を】
・何を送る？（タイトルのみ / 本文も / 作成者や作成日も）
・Notion側でどう見えてほしい？

【どこへ】                                   ← 最重要
・Notionのどのページ配下に作る？
・全ユーザー共通か、分けるのか
・送り先はどうやって設定する？

【失敗したら】
・エラーが返ったらどうする？
・ユーザーにどう伝える？次に何をすればよい？
```

> **「いつ」の最後の項目が効きます**
> 「1回送って終わり」か「同期し続ける」かで、**データ構造が変わります**。
>
> **「どこへ」が決まらないと1行も書けません**
> Notion APIは送り先の指定なしにページを作れません。

### 既存の言葉に意味を足していないか

既存システムへの追加のときだけ必要な観点です。

```
新しい機能を、既存の言葉にくっつけようとしていないか？
```

今回なら「公開（Publish）」です。

```
現状の「公開」: アプリ内で他ユーザーに見せる

「公開＝Notionにも送る」にすると:
  → 「公開」が2つの意味を持つ
  → あとで「片方だけしたい」が来たとき破綻する
```

**調べ方はコードに聞くこと。** 推測で議論しません。

```bash
grep -rn "Publish" frontend/src --include="*.tsx"
```

[NoteListPageTemplate.tsx](../../frontend/src/features/note/components/server/NoteListPageTemplate/NoteListPageTemplate.tsx) にこうありました。

```tsx
status: "Publish" as const, // 常に公開済みのみ
```

→ **「公開」＝アプリ内での露出スイッチ**だと確定します。

### 洗い出した不明点を仕分ける

20〜30個出ますが、**全部そのまま送ると相手は答えられません**。

```
「リトライは何回にしますか？」 → 相手「……わかりません」（判断材料がない）
「テーブルはどう分けますか？」 → 相手「……そちらで決めてください」

答えられない質問が混ざると、答えられる質問まで後回しにされる
```

判断基準はひとつです。

```
相手にしか答えられないか？
```

| | 相手にしか答えられない | 自分で決められる |
|---|---|---|
| 内容 | 業務の都合、優先順位、運用の実態 | 技術的な実現方法 |
| 例 | 「日報と週報は同じページでいい？」 | 「テーブルを分けるか」 |
| 例 | 「Notionが落ちてる間、公開できなくてよい？」 | 「リトライは何回か」 |

**相手が知っていて自分が知らないこと**だけを聞きます。

| 仕分け | 扱い | 個数の目安 |
|---|---|---|
| 聞く | 確認シートに載せる | 3〜5個 |
| 工数を示して選んでもらう | 「AならX日、BならY日」 | 1〜2個 |
| 決めて報告する | 仮説として書き、否定されなければ確定 | 8〜10個 |
| 決めて報告もしない | 相手に見せない | 15個以上 |
| やらないと明記する | スコープ外として書く | 3〜5個 |

> **「自分で決める」を増やすのがエンジニアの仕事**
> 何でも確認する人は、丁寧なのではなく**判断を放棄している**と受け取られます。
>
> ただし**工数に跳ね返るなら報告します**。
> 「OAuthで各自のNotionに送る」は技術判断ですが工数が3倍変わるので、
> 「共通トークンなら1週間、各自のNotionなら3週間」と伝えて判断してもらいます。

## Step 2. 仮説を作って確認する

### 質問リストではなく仮説を渡す

```
❌ 「どうしますか？」          → 相手が考える（重い）
❌ 「A・B・Cのどれですか？」   → 相手が選ぶ（まだ重い）
✅ 「たぶんこうだと思いますが、違いますか？」
                              → 否定するだけで済む（軽い）
```

ゼロから考えるより、目の前のものを否定する方が楽です。
「それは違う、実際はこうしたい」は考えなくても口から出ます。

仮説は、洗い出した不明点を**自分で全部埋めて**作ります。
「たぶんこうだろう」で構いません。外れたらその場でズレが1つ消えます。

### 確認シート

````markdown
## Notion連携について、こう作ろうと思っています

認識が合っているか見てください。違うところだけ教えてください。

### やりたいことの理解

ノートに書いた設計メモを、Notionにも置いておきたい。
Notionを見ている人にも共有できるようにしたい。
→ この理解で合っていますか？

### 想定している動き

1. ノートを「公開」すると、Notionにページが作られます
2. 公開中にノートを編集すると、Notionのページも更新されます
3. 「非公開」に戻すと、Notionのページも見えなくなります
4. 公開中のノートには「Notionで開く」リンクが出ます

つまり「公開 = 社内にもNotionにも出す」という扱いです。

### こう決めようと思っている点

| 項目 | こうします | 理由 |
|---|---|---|
| Notionのどこに作るか | テンプレートごとに置き場所のページを決めておきます<br>（例: 日報テンプレのノート →「日報」ページの下） | 日報と議事録が混ざると探しにくいはず |
| Notionに送るタイミング | ノートを公開したとき | 公開と連携を別々に操作するのは面倒なはず |
| 操作できる人 | そのノートを書いた本人だけ | いまの編集権限と同じ |
| ノートを削除したとき | Notionのページはそのまま残します | 消えると困る人がいそう |

### ⚠️ ここは自信がないので特に見てほしい

1. **Notionのどこに作るか**
   テンプレートごとに置き場所を決める想定です。
   実際はどう分けたいですか？
   「全部まとめて1つのページの下でいい」なら、もっと早く出せます。

2. **「公開」したら必ずNotionにも出る、でよいですか**
   「Mini Notion の中だけで共有したい。Notionには出したくない」
   というケースはありますか？
   あるなら、公開とは別に「Notionに送る」ボタンを用意します。
   後から分けるのは大変なので、いま決めたいです。

3. **Notion側が不調なとき、公開できなくなりますが大丈夫ですか**
   Notionへの書き込みに失敗したら、公開も中止する想定です。
   「公開したのにNotionには無い」という食い違いを防ぐためです。
   「不調でも、とりあえず社内には公開したい」なら、そう作れます。

### お願いしたいこと

設定作業はこちらでやります。お願いしたいのは2つだけです。

1. **ノートの置き場所にするページのURLを教えてください**

2. **そのページへのアクセスを許可してください**
   Notion では、APIキーを持っているだけでは書き込めません。
   「このページへの書き込みを許可する」操作が別に必要です。

   ```
   A. こちらでやる場合
      → そのページの権限をこちらのアカウントにいただければ設定します

   B. そちらでやる場合
      → ページを開いて「••• → 接続を追加」から Mini Notion を選ぶ
   ```

   一度やれば配下のページは全部書き込めるようになります。
   テンプレートを増やすたびにお願いすることはありません。
````

### このシートの型

```
□ 冒頭に「何がしたいのか」の理解を置く  → 全体像が先
□ 動きを時系列で説明する                → 相手が絵を描ける
□ 決定事項に理由を添える                → 違うときに言いやすい
□ 自信のない3点だけ意見を求める          → 全部見てもらう必要はない
□ 相手にやってもらう準備を伝える
□ 内輪の用語を使わない                  → 「送り先」では伝わらない
```

## Step 3. 結果をまとめる

### 返ってきた反応

| 項目 | 仮説 | 結果 |
|---|---|---|
| 権限・削除時の扱い・送る内容 | — | そのまま |
| 置き場所の単位 | テンプレートごと | 合っている。ただし**「日報と週報は同じページでいい」** |
| 公開との連動 | 連動させる | **「それでいい。公開＝外に出すでわかりやすい」** |
| Notion障害時 | 公開も止まる | **「困らない。中途半端に公開される方が困る」** |

**想定していなかった要望**

```
「一度送ったあと、ノートを直したらNotion側も直ってほしい。
 毎回新しいページができるのは困る」
```

仮説には「更新されます」と書いていましたが、相手にとっては**必須条件**でした。

**見送り:** ユーザーごとのNotionに送る / 一括連携 / 双方向同期

### 決まったこと（ミニ要件定義）

````markdown
## Notion連携 要件

### 目的
Mini Notion で書いた設計メモを Notion にも出し、
Notion を見ている人にも共有できるようにする。

### スコープ
- ノートを公開すると、Notion にページが作られる
- 公開中に編集すると、Notion のページも更新される
- 非公開に戻すと、Notion のページも見えなくなる
- 再公開すると、同じページが戻る（重複しない）

### 対象外
- ユーザーごとのNotionワークスペースへの連携
- 複数ノートの一括連携
- Notion 側での編集をこちらに取り込む（双方向同期）

### 仕様

| 項目 | 内容 |
|---|---|
| 操作する人 | ノートの作成者本人のみ |
| 置き場所 | テンプレートごとに設定した Notion ページの配下 |
| 送る内容 | タイトル、および全セクション（見出し付き） |
| タイミング | 公開・編集・非公開の操作に連動 |
| ノート削除時 | Notion のページは残す |
| 連携失敗時 | 公開・非公開の操作も行わない（元の状態のまま） |
| Notion 障害時 | ノートを公開できない（許容する） |
| どちらが正か | Mini Notion が正。Notion 側の編集は上書きされる |

### 前提条件
- 連携用インテグレーションを作成済み
- 置き場所のページがインテグレーションに許可済み
- テンプレートに置き場所が設定済み

### 設計で詰めること（次章）
- NotionのページIDをどこに持たせるか
- 外部API呼び出しをどこに置くか
````

> **ここまでが「何を作るか」**
> 「どう作るか」は次章です。
> この2つを混ぜると、依頼元との会話が技術論になって進みません。

---

## この章で起きたこと

チケットの3行には書かれていなかった事実が2つ出ました。

```
① 更新が必須だった
   「更新できるように」の一文が、NotionのページIDを保存する必要を意味していた
   → データ構造の変更が発生する

② 複数テンプレートが同じ置き場所を指す
   「日報と週報は同じページでいい」
   → ページIDの持たせ方に設計判断が必要
```

> **確認シートの価値**
> 仮説を具体的に書いたから「日報と週報は同じでいい」が引き出せました。
> 「置き場所はどうしますか？」と聞いていたら出てきていません。

## チェックリスト

```
【洗い出す】
□ 誰が / いつ / 何を / どこへ / 失敗したら を埋めたか
□ 既存の言葉に意味を足そうとしていないか
□ その言葉の意味をコードで確認したか（推測していないか）
□ 洗い出した項目を仕分けたか

【確認する】
□ 質問リストではなく、仮説の説明を渡したか
□ 冒頭に「何がしたいのか」の理解を置いたか
□ 決定事項に理由を添えたか
□ 相手にしか答えられない項目だけに絞ったか（3〜5個）
□ 内輪の用語を使っていないか

【まとめる】
□ 決まったことを文章にしたか
□ 「やらないこと」を明記したか
□ 前提条件を書いたか
```

## 参考: Notion API の事実

| 事実 | 出典 |
|---|---|
| ページ作成には `parent` の指定が**必須** | [Create a page](https://developers.notion.com/reference/post-page) |
| 親は `page_id` / `database_id` などから選ぶ | 同上 |
| ページ作成のレスポンスに `id` と `url` が返る。その `id` で後から更新できる | 同上 |
| **物理削除はできない**。`in_trash: true` でゴミ箱へ入れるのみ。`false` で復元（同じID） | [Archive a page](https://developers.notion.com/reference/archive-a-page) |
| **ページ配下**では `title` のみ設定可能（DB配下はスキーマに適合が必要） | [Working with databases](https://developers.notion.com/docs/working-with-databases) |
| URLの32文字の英数字がID（ハイフン有無どちらでも可） | 同上 |
| **APIキーだけでは書き込めない。** 許可したページ以外はアクセス不可（404 `object_not_found`） | [Internal connections](https://developers.notion.com/guides/get-started/internal-connections) |
| 権限付与のAPIは無い。開発者ポータルかNotion UIから手動で行う | 同上 |
| **親ページを許可すれば配下のページにも権限が継承される** | 同上 |
| 内部インテグレーションはリダイレクトURI・公開サーバー・Webhook受信が**すべて不要**。**localhost からそのまま呼べる** | 同上 |
| Business / Enterprise プランではインテグレーション作成が既定で制限される | [Create an integration](https://developers.notion.com/docs/create-a-notion-integration) |
