# 機能追加の進め方

「Notion連携したい」。この程度の情報で降ってくるタスクを、リリースまで持っていく手順を扱う。
コードの書き方ではなく、進め方のドキュメント。

---

## 題材

Mini Notion に、書いたノートを Notion へ連携する機能を追加する。

[要件定義書](../global_design/01_requirements.md) の「将来の拡張予定」に挙げられていた項目が、
ついにタスクとして降りてきた、という想定。

```
[タスク] ノートのNotion連携

作成したノートをNotionにも連携して
更新できるようにしたい。
Notion APIを使う。
```

記載はこれだけ。仕様書はない。この状態から始める。

```
① 不明点を洗い出す
② 設計方針を決める
③ 影響範囲を調べる
④ テスト方針とQAケースを決める
⑤ 段取りを組む（PR分割）
⑥ 実装する（テストも同時に）
⑦ 完成確認
```

実装（⑥）は全体の一部でしかない。設計と段取りに時間をかけるほど、実装は速く安全になる。

テストは一つの工程ではない。粒度ごとに作るタイミングが違う。

```
QAケース（受け入れ基準）        → 設計直後（④）
ユニット/インテグレーション      → 実装と同時（⑥）
本物のNotionと繋いで確認      → 最後（⑦）
```

## 目次

### [01_requirement_hearing.md](./01_requirement_hearing.md) — 不明点の洗い出し

数行のタスクから30個以上の確認事項を機械的に出す。
5観点（誰が / いつ / 何を / どこへ / 失敗したら）、外部API連携に特有の観点（認証・冪等性・レート制限）、
既存概念への影響を疑う観点。

ただし観点リストは**自分用**。相手に渡すのは質問リストではなく、
「こう作るつもりだ」という**仮説の確認シート**にする。
相手は否定するだけで済み、全体像も伝わる。聞くべき項目の絞り方も扱う。

Notion APIの事実（親ページ指定の必須性、ページ配下とDB配下の違い）も出典付きで記載。

### [02_design_policy.md](./02_design_policy.md) — 設計方針の決定

4つの論点について、選択肢を並べ判断軸で比較する。

- 論点A: 既存の「公開」と連携を紐づけるか
- 論点B: 送り先をどこに持たせるか（正規化の判断）
- 論点C: 連携状態をどう記録するか
- 論点D: 外部API呼び出しをどこで実行するか（トランザクション境界）

各論点に推奨案・理由・見直し条件を記載。チームレビューに出す際の論点提示の型も含む。

### [03_impact_analysis.md](./03_impact_analysis.md) — 影響範囲とデグレ分析

変更を「追加」と「変更」に分け、リスクの所在を特定する。
既存テストのカバレッジ実測値と、守られる範囲・守られない範囲。
リスク一覧と対策、ロールバック手順、レビュー観点。

### [04_test_strategy.md](./04_test_strategy.md) — テスト方針とQAケース

実装前に「どう動けば合格か」を決める。仕様が決まった時点で書ける。

層ごとのテスト方法と目標カバレッジ、外部APIのモック方針、
テストしやすい構造にするための制約。
QAケース18件（正常系・権限・設計遵守・異常系・デグレ確認）とエラーメッセージの文言。

### [05_work_breakdown.md](./05_work_breakdown.md) — 段取りとPR分割

6本のPRへの分割案。依存関係、並行可能な作業、各PRの受け入れ基準。
デグレリスクがどのPRに集中するか。PRテンプレート。

### [06_implementation.md](./06_implementation.md) — 実装（AI活用）

設計ドキュメントをプロンプトに変換する。PR単位の指示例を6本分。
ユニット/インテグレーションテストを実装と同じPRで書く（gomock / httptest の実例）。
AIが間違えやすいポイントと先回りの指示。生成コードのレビュー観点。

### [07_completion_check.md](./07_completion_check.md) — 完成確認

ローカル環境で本物の Notion と繋いで動かす。
モックでは見つからない問題（文字化け、ブロック上限、許可漏れ）の確認。
完成チェックリストと、つまずきやすい箇所の一覧。

## このドキュメントの方針

### 判断の根拠を残す

結論だけでなく、検討した選択肢・判断軸・見直し条件まで書く。
レビューで「なぜこれ？」と問われたときに、議論を最初からやり直さないため。

### 推測で書かない

既存の仕様はコードを読んで確認する。カバレッジは実測する。
外部APIの挙動は公式ドキュメントで裏を取る。

### 実在するコードを題材にする

`backend-clean/` は実際に動くアプリケーション。
このコードを実際にどう変更するかを扱う。

```
[タスク] ノートのNotion連携
    │
    │ ① 不明点の洗い出し ──────── 01_requirement_hearing.md
    │    30個の確認事項
    ▼
    │ ② 設計方針の検討 ────────── 02_design_policy.md
    │    選択肢と判断軸
    ▼
    │ ③ 影響範囲・デグレ分析 ────── 03_impact_analysis.md
    │    どこが壊れうるか
    ▼
    │ ④ テスト方針・QAケース ────── 04_test_strategy.md
    │    どう動けば合格か
    ▼
    │    ← チームレビュー・方針決定
    ▼
    │ ⑤ 段取り・PR分割 ────────── 05_work_breakdown.md
    │    6本のPR
    ▼
    │ ⑥ 実装＋テスト ───────────── 06_implementation.md
    │    設計書とQAケースをプロンプトに
    ▼
    │ ⑦ 完成確認 ──────────────── 07_completion_check.md
    │    本物のNotionと繋いで確認
    ▼
  完成
```
