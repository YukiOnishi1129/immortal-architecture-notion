# 機能追加の進め方

「Notion連携したい」。この程度の情報で降ってくるタスクを、
完成まで持っていく手順を扱う。

コードの書き方ではなく、進め方のドキュメント。

---

## 題材

Mini Notion に、書いたノートを Notion へ連携する機能を追加する。

[要件定義書](../global_design/01_requirements.md) の「将来の拡張予定」に
挙げられていた項目が、タスクとして降りてきた想定。

```
[タスク] ノートのNotion連携

作成したノートをNotionにも連携して
更新できるようにしたい。
Notion APIを使う。
```

記載はこれだけ。仕様書はない。

```
① 不明点を洗い出して確認する
② 設計方針と影響範囲を決める
③ テスト方針とQAケースを決める
④ 段取りを組む（PR分割）
⑤ 実装する（テストも同時に）
⑥ 本物のNotionと繋いで確認する
```

実装（⑤）は全体の一部でしかない。

---

## 目次

### [01_requirement_hearing.md](./01_requirement_hearing.md) — 不明点の洗い出しと確認

数行のタスクから確認事項を機械的に出す。
5観点（誰が / いつ / 何を / どこへ / 失敗したら）、既存概念への影響を疑う観点。

ただし観点リストは**自分用**。相手に渡すのは質問リストではなく、
「こう作るつもりだ」という**仮説の確認シート**にする。

最後に、決まったことをミニ要件定義としてまとめる。

### [02_design_policy.md](./02_design_policy.md) — 設計方針と影響範囲

**ユースケースを洗い出してから、既存コードとの差分を出す。**
要件だけを起点にすると、要件に書かれていない操作（既存データの救済、
失敗時の挙動）が落ちる。差分から「決めること」が7つ出る。

```
① 公開と連携をどう繋ぐか
② 失敗したらどうするか
③ NotionのページIDをどこに持たせるか
④ ReadModel に何を載せるか
⑤ 親ページが未設定のときどうするか
⑥ 外部API呼び出しをどこで実行するか
⑦ 既存データをどう救済するか
```

決定と同時に「触る範囲」まで確定させる。

方針だけ相談しても意味がないので、リスク一覧・テストカバレッジ実測・
ロールバック手順まで含めて、開発チームに渡せる形にする。

### [03_test_strategy.md](./03_test_strategy.md) — テスト方針とQAケース

実装前に「どう動けば合格か」を決める。仕様が決まった時点で書ける。

層ごとのテスト方法と目標カバレッジ、外部APIのモック方針、
テストしやすい構造にするための制約。
QAケース（正常系・権限・設計遵守・異常系・デグレ確認）とエラーメッセージの文言。

### [04_work_breakdown.md](./04_work_breakdown.md) — 段取りとPR分割

7本のPRへの分割案。依存関係、並行可能な作業、各PRの受け入れ基準。
デグレリスクがどのPRに集中するか。PRテンプレート。

### [05_implementation.md](./05_implementation.md) — 実装（AI活用）

設計ドキュメントをプロンプトに変換する。PR単位の指示例。
ユニット/インテグレーションテストを実装と同じPRで書く。
AIが間違えやすいポイントと先回りの指示。

### [06_completion_check.md](./06_completion_check.md) — 完成確認

ローカル環境で本物の Notion と繋いで動かす。
モックでは見つからない問題（文字化け、ブロック上限、許可漏れ）の確認。
完成チェックリストと、つまずきやすい箇所の一覧。

## このドキュメントの方針

### 決定と影響範囲はセットで出す

「こう作ります」だけでは相談になりません。
「既存のここを触ります、だから壊れません」まで揃えて渡します。

### 判断の根拠を残す

結論だけでなく、検討した選択肢・判断軸・見直し条件まで書く。
レビューで「なぜこれ？」と問われたときに、議論を最初からやり直さないため。

### 推測で書かない

既存の仕様はコードを読んで確認する。カバレッジは実測する。
外部APIの挙動は公式ドキュメントで裏を取る。

### 実在するコードを題材にする

`backend-clean/` は実際に動くアプリケーション。
このコードを実際にどう変更するかを扱う。

## 全体の流れ

```
[タスク] ノートのNotion連携
    │
    │ ① 不明点の洗い出しと確認 ──── 01_requirement_hearing.md
    │    依頼元に確認シートを渡す
    ▼
    │ ② 設計方針と影響範囲 ──────── 02_design_policy.md
    │    開発チームに設計を渡す
    ▼
    │ ③ テスト方針・QAケース ────── 03_test_strategy.md
    │    どう動けば合格か
    ▼
    │ ④ 段取り・PR分割 ─────────── 04_work_breakdown.md
    │    7本のPR
    ▼
    │ ⑤ 実装＋テスト ───────────── 05_implementation.md
    ▼
    │ ⑥ 完成確認 ──────────────── 06_completion_check.md
    ▼
  完成
```
