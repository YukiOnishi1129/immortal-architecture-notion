## 設計判断の型

技術的な議論は、感情論や声の大きさで決まりがちです。
それを防ぐのが**この型**です。

```
┌─────────────────────────────────────┐
│ 1. 選択肢を全部並べる（3つ程度）        │
│ 2. 判断軸を先に決める                  │
│ 3. 軸ごとに各案を評価する（表にする）    │
│ 4. 推奨案とその理由を書く               │
│ 5. 「将来こうなったら見直す」を書く      │
└─────────────────────────────────────┘
```

> ⚠️ **やってはいけないこと**
> 結論だけ書く。→ レビューで「なんでこれ？」となり、議論が最初からやり直しになります。
> **選択肢と判断軸を残すことが、ドキュメントの価値です。**

## 論点A: 既存の「公開」と紐づけるか

**論点:** 「ノートを公開したら、自動でNotionにも送る」は妥当か。

一見自然に見えますが、既存の「公開」が何を意味しているかを確かめないと判断できません。

### まず事実確認：「公開」は何のためにあるか

**推測で議論しないこと。** コードを読めば答えがあります。

```bash
grep -rn "Publish" frontend/src --include="*.tsx"
```

[NoteListPageTemplate.tsx](../../frontend/src/features/note/components/server/NoteListPageTemplate/NoteListPageTemplate.tsx) にこうありました。

```tsx
status: "Publish" as const, // 常に公開済みのみ
```

| 画面 | 表示されるノート |
|---|---|
| `/notes`（みんなのノート） | **Publish のみ** |
| `/my-notes`（自分のノート） | Draft も Publish も |

**つまり「公開」＝ アプリ内で他ユーザーに見せるスイッチ**です。

### ここで出てくる問い

```
Notionにも出せるようになったら、
アプリ内だけで見える「公開」は何のためにある？
```

役割を整理すると、こうなります。

| | Mini Notion の `/notes` | Notion |
|---|---|---|
| 見え方 | **構造化されたまま**（テンプレート・セクション単位） | ただのページ |
| できること | 検索・比較・テンプレート再利用 | 読むだけ |
| 読む人 | 同じフォーマットで書く人 | Notionしか見ない人 |

役割は違いますが、**「外に出す」という意味では同じ**です。
2つのスイッチを別々に管理させるのはユーザーにとって面倒です。

### 選択肢

```
案A-1  公開に連動させる
       Draft → Publish でNotionへ送り、Publish → Draft でNotionから下げる

案A-2  別の操作にする
       公開とは別に「Notion連携」ボタンを置く

案A-3  公開に連動＋個別にON/OFF
       公開時に連携するが、ノートごとに「連携しない」も選べる
```

### 判断軸で比較する

| 判断軸 | 案A-1<br>公開に連動 | 案A-2<br>別操作 | 案A-3<br>連動＋設定 |
|---|:---:|:---:|:---:|
| **概念がわかりやすいか** | ✅ 公開＝外に出す | ❌ スイッチが2つ | ⚠️ 例外あり |
| **ユーザーの手間** | ✅ 1操作 | ❌ 2操作 | ✅ 1操作 |
| **影響範囲の狭さ** | ⚠️ ChangeStatus改修 | ✅ 追加のみ | ❌ 広い |
| **デグレリスク** | ⚠️ 既存機能を触る | ✅ 既存は無変更 | ❌ 高い |
| **実装コスト** | ⚠️ 中 | ✅ 小 | ❌ 大 |

### 📌 推奨: 案A-1（公開に連動させる）

**理由:**

```
1. 「公開」の意味が一本化される
   → 公開 = 外に出す（アプリ内にもNotionにも）
   → 「アプリ内だけの公開って何のため？」という疑問が消える

2. ユーザーが2つのスイッチを管理しなくて済む
   → 「公開したのにNotionに出てない」が起きない

3. 非公開に戻したらNotionからも下がる
   → 「見せたくないものが外に残る」事故を防げる
```

> **案A-2（別操作）を選ばなかった理由**
> 影響範囲は狭くなりますが、**ユーザーから見て概念が2つになります**。
> 「公開」と「Notion連携」の違いを説明し続けることになり、
> 「公開したのにNotionにないんだけど」という問い合わせが発生します。
>
> **実装の都合より、概念の一貫性を優先しました。**

### 動作の定義

| 操作 | Notion側 | 失敗したら |
|---|---|---|
| Draft → Publish（初回） | ページを作成 | 公開しない |
| Draft → Publish（2回目以降） | ゴミ箱から戻す（`in_trash: false`） | 公開しない |
| Publish → Draft | ゴミ箱に入れる（`in_trash: true`） | 非公開にしない |
| 公開中のノートを編集 | ページを更新 | 編集を保存しない |
| 下書きのノートを編集 | 何もしない | — |
| ノートを削除 | Notionページは残す（要件どおり） | — |

> **Notion APIに物理削除はありません**
> できるのは `in_trash: true` でゴミ箱に入れることだけで、
> 同じページIDで復元できます（[Archive a page](https://developers.notion.com/reference/archive-a-page)）。
>
> この仕様は今回の設計に好都合です。
> 再公開時に**新しいページを作らずに済みます**。

### 既存データの扱い

すでに公開されているノートは、Notionに連携されていません。

```
リリース時点:
  公開済みノートが50件ある
    ↓
  どれもNotionにページがない
    ↓
  放置すると、いつまでも連携されない
```

対策として、**詳細ページに手動連携ボタンを置きます**。

```
公開済み & 未連携のノート
  → 「Notionに未連携です [連携する]」と表示
  → 押すと連携される（以降は自動で同期）
```

> このボタンは**既存データの救済と、失敗時の再試行を兼ねます**。
> 連動させる設計でも、手動の入口は必要です。

**見直すタイミング:**
```
「公開はしたいがNotionには出したくない」が複数出たら、
案A-3（連動＋個別ON/OFF）への移行を検討する。
```

## 論点A-2: 連携が失敗したらどうするか

公開と連動させると決めた以上、**失敗時の扱いを決めないと作れません**。

### 選択肢

```
案1  連携が失敗しても、公開/非公開は成功させる
     → 状態がずれるが、Notion障害でアプリが止まらない

案2  連携が失敗したら、公開/非公開も失敗させる（ロールバック）
     → 状態が常に一致するが、Notion障害時は公開できない
```

### 判断軸で比較する

| 判断軸 | 案1<br>片方だけ成功 | 案2<br>ロールバック |
|---|:---:|:---:|
| **状態の一貫性** | ❌ ずれる | ✅ 常に一致 |
| **ユーザーへの説明** | ❌ 「公開済みだがNotion未連携」を説明する必要 | ✅ 公開＝Notionにある |
| **Notion障害時** | ✅ 公開はできる | ❌ 公開できない |
| **実装の複雑さ** | ❌ ずれた状態の表示・再試行が必要 | ✅ 単純 |

### 📌 決定: 案2（ロールバック）

**理由:**

```
1. 論点Aで「公開 = 外に出す」に一本化した
   → 「公開されているがNotionにはない」は、その定義に反する
   → 中途半端な状態を認めると、概念の一本化が崩れる

2. 非公開時は絶対にロールバックすべき
   → Notionから消せないのに「非公開になりました」は事故
   → なら公開時も揃える方が、ルールとして単純

3. 失敗したことがその場でわかる
   → 「公開できませんでした」と即座に伝わる
   → ユーザーはリトライすればよい
   → 「公開したつもりが連携されていなかった」に後で気づくより良い
```

### トレードオフを引き受ける

この設計には**明確なコストがあります**。

```
Notionが落ちている間、ノートを公開できない
   ↓
外部サービスの障害が、自社機能を止める
```

一般には避けるべき構造です。それでも選ぶのは、
**状態がずれる方が実害が大きい**と判断したためです。

> ⚠️ **この判断は必ずレビューにかけること**
> 「外部障害で自社機能が止まる」は重大な設計判断です。
> エンジニアが独断で決めず、
> 「Notionが落ちている間は公開できなくなりますが、よいですか」
> と明示して合意を取ります。
>
> 相手が「それは困る」と言えば案1に倒します。
> **判断材料を渡して決めてもらう**のがここでの仕事です。

### チームレビューに出すときの型

このドキュメントをチームに投げるときは、**論点を明示**します。

```markdown
## 論点B: 送り先をどこに持たせるか

ヒアリング結果は「テンプレートごとに送り先を変えたい」でした。

`templates` に `notion_parent_id` を足せば済むように見えますが、問題があります。

### 問題: 複数テンプレートが同じ送り先を指す

```
日報テンプレート     → Notionの「日報」ページ
週報テンプレート     → Notionの「日報」ページ  ← 同じ！
議事録テンプレート   → Notionの「会議」ページ
```

**テンプレートに直接持たせると、同じIDが複数行に重複します。**

```sql
-- templates テーブル
| id  | name     | notion_parent_id |
|-----|----------|------------------|
| t1  | 日報     | abc123...        |
| t2  | 週報     | abc123...        |  ← 重複
| t3  | 議事録   | xyz789...        |
```

送り先を変えたいとき、**全部の行を更新**しないといけません。
更新漏れがあれば、一部のノートだけ古い場所に飛びます。

### 選択肢

#### 案B-1: templates に直接持たせる

```sql
ALTER TABLE templates ADD COLUMN notion_parent_id TEXT;
```

新テーブル不要で実装は最小。ただし同じ送り先が複数行に重複します。

#### 案B-2: 送り先テーブルを新設して参照

```sql
CREATE TABLE notion_destinations (
    id UUID PRIMARY KEY,
    name TEXT NOT NULL,           -- 「日報置き場」など人間が読める名前
    parent_page_id TEXT NOT NULL,
    created_at TIMESTAMPTZ
);

ALTER TABLE templates
  ADD COLUMN notion_destination_id UUID REFERENCES notion_destinations(id);
```

```
-- notion_destinations          -- templates
| id | name      | page_id |    | id | name   | dest_id |
|----|-----------|---------|    |----|--------|---------|
| d1 | 日報置き場 | abc123  |    | t1 | 日報   | d1      |
| d2 | 会議室    | xyz789  |    | t2 | 週報   | d1      | ← 同じ送り先
                                | t3 | 議事録 | d2      |
```

送り先が1箇所に正規化され、名前も付けられます。テーブルが1つ増えるのがコスト。

#### 案B-3: 環境変数で全体固定

```bash
NOTION_PARENT_PAGE_ID=abc123...
```

実装は最小ですが、テンプレートごとに変えられず**要件を満たしません**。

### 判断軸で比較する

| 判断軸 | 案B-1<br>templates直接 | 案B-2<br>送り先テーブル | 案B-3<br>環境変数 |
|---|:---:|:---:|:---:|
| **要件を満たすか** | ✅ | ✅ | ❌ 満たさない |
| **データの重複** | ❌ 重複する | ✅ 正規化 | ✅ 重複なし |
| **送り先変更の容易さ** | ❌ 複数行更新 | ✅ 1行更新 | ✅ 環境変数1つ |
| **実装コスト** | ✅ 小 | ⚠️ 中 | ✅ 最小 |
| **将来の拡張性** | ❌ 低い | ✅ 高い | ❌ 低い |
| **管理画面の作りやすさ** | ⚠️ IDを直接入力 | ✅ 名前で選択 | ❌ 画面なし |

### 推奨: 案B-2（送り先テーブルを新設）

**理由:**

```
1. ヒアリングで「テンプレートごと」が確定 → 案B-3は脱落

2. 「複数テンプレートが同じ送り先」は実際に起きる
   → 案B-1だと更新漏れの事故が起きる

3. 送り先に名前を付けられる価値が大きい
   → 管理画面で「abc123...」から選ばせるのは非現実的
   → 「日報置き場」から選べる
```

> **段階的に進める案もあります**
> 第1弾は案B-1（templates直接）で出し、
> 運用してから案B-2へ移行する判断もありえます。
> ただし移行時にデータ移行が必要になるため、
> **最初から案B-2を選ぶほうが総コストは低い**と判断しました。

### 検討したが採らなかった案: プロジェクト単位

レビューでこういう指摘が出ました。

```
「1つのテンプレートを、複数のプロジェクトで使い回したい。
  日報テンプレは A プロジェクトでも B プロジェクトでも使う。
  テンプレート単位だと表現できないのでは？」
```

正しい指摘です。対案としてこういう構造が考えられます。

```
projects テーブルを新設し、notes に project_id を持たせる
  → ノートごとに「どのプロジェクトの下に送るか」が決まる
  → テンプレートは自由に使い回せる
```

**それでも採用しませんでした。**

```
理由: 運用で回避できるため

「A日報」「B日報」のようにテンプレートを分ければ、
プロジェクトごとの送り分けは実現できる

得られるもの: テンプレートの使い回し
失うもの:     新テーブル、notes への列追加、
              プロジェクト管理画面、既存ノートへの割り当て
```

> **新しい概念を足す前に、既存の概念で回らないか考える**
> 「プロジェクト」はこのアプリに存在しない概念です。
> 導入すれば画面もデータも増え、**Notion連携という主題がぼやけます**。
>
> テンプレートを複製する手間は残りますが、
> **今回のスコープでは許容できる**と判断しました。

**見直すタイミング:**
```
・テンプレートの複製が10個を超えて管理しきれなくなったら
・「ユーザーごとに自分のNotionへ送りたい」が出たら
  → notion_destinations に owner_id を足す拡張を検討
```

## 論点B-2: 送り先が未設定なら公開できない

論点Aで「公開＝Notionに出す」と一本化しました。
ということは、**送り先が決まっていないノートは公開できない**ことになります。

```
テンプレートに送り先が未設定
    ↓
どこに送ればいいかわからない
    ↓
公開できない（エラーにする）
```

> **「Notion連携をスキップして公開」は選ばなかった**
> 未設定なら連携せずに公開する、という逃げ道もあります。
> しかしそれを認めると「公開されているがNotionにない」状態が生まれ、
> **論点Aの一本化が崩れます**。

### 既存データの移行

この決定には**リリース時の作業が伴います**。

```
機能リリース時点
    ↓
既存のテンプレートは全部 notion_destination_id が NULL
    ↓
そのままリリースすると、誰も公開できなくなる
```

対応は**リリース前の手作業**とします。

```
1. Notion側に送り先ページを用意する
2. 管理画面から notion_destinations を登録する
3. 既存の全テンプレートに送り先を割り当てる
4. 割り当て漏れがないことを確認してからリリース
```

> **自動移行（デフォルト送り先を作って一括設定）は採りませんでした**
> ```
> 「未分類」のような送り先を作って全部に割り当てれば楽ですが、
> Notion側に親ページがまだ無い場合もあります。
> テンプレートの数が少ないうちは、
> どこに送るかを1つずつ決めた方が確実です。
> ```
>
> **テンプレートが数十個ある規模なら、この判断は変わります。**

### 新規テンプレート作成時

```
送り先の選択を必須にする
  → 未設定のテンプレートが新たに生まれない
  → 「公開できないテンプレート」が作られるのを防ぐ
```

## 論点C: 連携状態をどう記録するか

### 必須要件: NotionのページIDを保存する

第1章で判明したとおり、**更新に追従するにはページIDの保存が必須**です。

```
1回目: POST /v1/pages → { id: "page-abc", url: "..." }
                              ↓ 保存する
2回目: PATCH /v1/pages/page-abc → 同じページを更新 ✅

保存しなかった場合:
2回目: POST /v1/pages → 新しいページができる ❌ 重複
```

### さらに必要なもの: 失敗の記録

ヒアリングで「**公開は成功させ、連携だけ失敗とする**」と決まりました。
ということは、**失敗した事実を残す**必要があります。

```
失敗を記録しないと:
  ユーザー「連携できてる？」
  システム「わかりません」
  → 再試行もできない
```

### 選択肢

#### 案C-1: notes テーブルに列を追加

```sql
ALTER TABLE notes
  ADD COLUMN notion_page_id TEXT,
  ADD COLUMN notion_sync_status TEXT,
  ADD COLUMN notion_synced_at TIMESTAMPTZ,
  ADD COLUMN notion_error_message TEXT;
```

JOINなしで取れて実装は単純。ただし notes が連携の関心事で太り、
将来「Notion以外にも連携」となったとき列が増え続けます。

#### 案C-2: 連携テーブルを新設

```sql
CREATE TABLE note_notion_syncs (
    note_id UUID PRIMARY KEY REFERENCES notes(id) ON DELETE CASCADE,
    notion_page_id TEXT,
    notion_page_url TEXT,
    status TEXT NOT NULL,        -- pending / synced / failed
    error_message TEXT,
    last_synced_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

notes が汚れず、連携という概念が独立します。JOINが必要になるのがコスト。

### 判断軸で比較する

| 判断軸 | 案C-1<br>notes に列追加 | 案C-2<br>連携テーブル |
|---|:---:|:---:|
| **既存テーブルへの影響** | ❌ notes が太る | ✅ notes 無変更 |
| **関心の分離** | ❌ 混ざる | ✅ 分離 |
| **実装コスト** | ✅ 小 | ⚠️ 中 |
| **読み取り性能** | ✅ JOIN不要 | ⚠️ JOIN必要 |
| **将来の拡張性** | ❌ 列が増え続ける | ✅ 高い |
| **ReadModelへの影響** | ❌ 再構築が必要 | ✅ 影響を制御できる |

### 推奨: 案C-2（連携テーブルを新設）

**理由:**

```
1. notes は「ノートそのもの」を表すテーブル
   外部連携の状態は別の関心事

2. ⚠️ 重要: このアプリはCQRSで ReadModel を持っている
   notes に列を足すと、note_read_models の再構築も必要になり
   影響範囲が一気に広がる（第3章で詳述）

3. 連携は「あとから足した機能」なので、
   既存テーブルを太らせないほうが剥がしやすい
```

---

## 論点D: 外部API呼び出しをどこで実行するか

論点A-2で「連携が失敗したら公開もしない」と決めました。
ここで**一見、矛盾が生じます**。

```
ロールバックしたい
   ↓
「同じトランザクションに入れればいいのでは？」
   ↓
でも、トランザクションの中で外部APIを呼ぶのは厳禁
```

### なぜトランザクション内で外部APIを呼んではいけないか

```go
// ❌ 絶対にやってはいけない
err = u.tx.WithinTransaction(ctx, func(txCtx context.Context) error {
    if err := u.notes.UpdateStatus(txCtx, id, status); err != nil {
        return err
    }
    return u.notion.CreatePage(txCtx, page)   // ← 危険
})
```

```
Notion APIが遅い（3秒かかる）
    ↓
その3秒間、DBのトランザクションが開きっぱなし
    ↓
行ロックが保持され続ける
    ↓
同じ行を触る他のリクエストが待たされる
    ↓
Notionがタイムアウト（30秒）すると…
    ↓
30秒間ロック保持 → コネクションプール枯渇 → 全体障害
```

> 🚨 **鉄則: トランザクションの中で外部APIを呼ばない**
> DBトランザクションは「速く始めて速く終わる」もの。
> ネットワーク越しの呼び出しは、いつ終わるかわかりません。

### 解決: Notionを先に呼ぶ

矛盾は**順序を変えるだけで解けます**。

```
❌ DBを更新 → Notion呼び出し → 失敗したらDBを戻す
   （戻す処理が必要。トランザクションに入れたくなる）

✅ Notion呼び出し → 成功したらDBを更新
   （失敗したらDBを触らない。戻す処理が不要）
```

```go
// ✅ 正しい順序

// ステップ1: 先にNotionを呼ぶ（トランザクションの外）
result, err := u.notion.CreatePage(ctx, parentID, title, blocks)
if err != nil {
    // DBは何も変えていないので、戻す処理が要らない
    return fmt.Errorf("Notionへの連携に失敗しました: %w", err)
}

// ステップ2: 成功したのでDBを更新（トランザクションの中）
return u.tx.WithinTransaction(ctx, func(txCtx context.Context) error {
    if _, err := u.notes.UpdateStatus(txCtx, id, note.StatusPublish); err != nil {
        return err
    }
    if err := u.syncRepo.Save(txCtx, id, result.PageID, result.URL); err != nil {
        return err
    }
    return u.readModelRepo.Upsert(txCtx, toReadModel(n))
})
```

> **ロールバックが「不要」になる**
> DBを変更する前にNotionを呼ぶので、失敗したときに戻すものがありません。
> トランザクションは短いまま、状態の一貫性も守れます。

### 残る穴: Notion成功後にDB更新が失敗したら

この順序にも、1つだけ隙間があります。

```
Notionにページ作成 → 成功
    ↓
DBの更新 → 失敗（DB障害など）
    ↓
Notionにはページがあるが、アプリは下書きのまま
```

**この状態は許容します。**

```
1. 被害が小さい
   → Notionに「まだ公開していないノート」が出るだけ
   → 逆（公開済みなのにNotionにない）より軽い

2. 次の公開操作でほぼ解消する
   → もう一度公開すれば、新しいページが作られて連携される
   → 前のページはNotion側に残るが、手動で消せる
```

> **完全な整合性は諦める**
> DBと外部サービスを跨いだ完全な整合性は、
> 分散トランザクションなしには実現できません。
> **どちらにずれるかを選び、軽い方に倒す**のが現実的な設計です。

### 非公開にするときの順序

公開と同じ考え方です。

```go
// ステップ1: 先にNotionをゴミ箱へ
if err := u.notion.Trash(ctx, sync.NotionPageID); err != nil {
    return fmt.Errorf("Notionから削除できませんでした: %w", err)
}

// ステップ2: 成功したのでDBを更新
return u.tx.WithinTransaction(ctx, func(txCtx context.Context) error {
    ...UpdateStatus(txCtx, id, note.StatusDraft)...
})
```

ここでも「Notionから消えたがアプリは公開のまま」というずれが起きえますが、
**見せたくないものは既に消えている**ので実害はありません。

## 決定事項まとめ

| 論点 | 決定 | 主な理由 |
|---|---|---|
| **A. 公開との関係** | **公開に連動させる** | 「公開＝外に出す」で概念を一本化。スイッチを2つ持たせない |
| **A-2. 失敗時** | **ロールバックする** | 状態のずれを認めない。外部障害で公開が止まるコストは引き受ける |
| **B. 送り先の持たせ方** | テンプレート単位。送り先テーブルを新設して参照 | 複数テンプレートが同じ送り先を指すため。プロジェクト概念の導入は見送り |
| **B-2. 送り先未設定** | **公開できない**（エラー） | 「公開＝Notionにある」を崩さないため。既存分はリリース前に手作業で設定 |
| **C. 連携状態の記録** | 連携テーブルを新設 | notes/ReadModel への影響を避ける |
| **D. 外部API実行位置** | **トランザクション外。かつNotionを先に呼ぶ** | ロック長期化を避けつつ、ロールバック処理を不要にする |

### 決定に基づくデータ構造

```
┌─────────────────────┐
│ notion_destinations │  送り先マスタ（新規）
│ - id                │
│ - name              │  「日報置き場」
│ - parent_page_id    │  NotionのページID
└──────────▲──────────┘
           │ 参照
┌──────────┴──────────┐
│ templates           │  既存（列を1つ追加）
│ - id                │
│ - name              │
│ + notion_dest_id    │  ← 追加
└──────────▲──────────┘
           │ 参照（既存）
┌──────────┴──────────┐      ┌──────────────────────┐
│ notes               │      │ note_notion_syncs    │  連携状態（新規）
│ - id                │◄─────┤ - note_id            │
│ - title             │ 1:1  │ - notion_page_id     │  更新・復元用のID
│ - status            │      │ - notion_page_url    │
│ （カラムは変更なし）  │      │ - last_synced_at     │
└─────────────────────┘      └──────────────────────┘
```

> **notes テーブルのカラムは変わりません**
> status の**意味**は変わりますが、**構成は無変更**です。
> 変わるのは「status を変えるときに何が起きるか」だけです。

### 影響を受ける既存コード

公開に連動させる決定により、**既存メソッドを2つ触ります**。

| メソッド | 変更内容 |
|---|---|
| `ChangeStatus` | 公開/非公開の前にNotion連携を実行 |
| `Update` | 公開中のノートならNotionも更新 |

> ⚠️ **ここが最大のリスクです**
> `NoteCommandInteractor` には**テストがありません**（第3章で詳述）。
> テストのないコードを2箇所変更することになります。
>
> 対策: 変更前に、既存の振る舞いに対するテストを先に書きます。

### 合意が必須（これが覆ると設計が変わる）

  → 設定していないテンプレートでは公開できなくなります
  → 作業漏れがあると、そのテンプレートのノートが公開不能になります

- 論点A-2: **Notionが落ちている間、ノートを公開できなくなります**
  → 外部サービスの障害が自社機能を止める構造です
