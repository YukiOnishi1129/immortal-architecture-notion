# ③ テスト方針とQAケース

> **この章でやること**
> 実装に入る前に「どう動けば合格か」を決めておく。

---

## テストは粒度ごとに作るタイミングが違う

```
QAケース（受け入れ基準）     → 設計直後（この章）
ユニット/インテグレーション  → 実装と同時（第5章）
本物と繋いだ確認            → 最後（第6章）
```

**QAケースは仕様が決まった時点で書けます。** 実装を待つ必要がありません。

```
❌ 実装が終わってからテストを考える
   → 「これテストしづらい構造だな」と気づく → 作り直し

✅ 実装前に決めておく
   → テストしやすい構造で実装できる
   → AIに実装させるとき、テスト要件も一緒に渡せる
```

---

## テスト方針

### 外部APIはモックに差し替える

自動テストで本物の Notion API を呼ばない、という方針です。

```
1. Notionが落ちるとCIが赤くなる（自分のコードは正しいのに）
2. 遅い（1回1秒 × テスト100個）
3. レート制限に引っかかる
4. テストのたびにゴミページができる
5. APIキーをCIに置く必要がある
6. 異常系をテストできない  ← 決定的
```

「500が返ってきたとき」を本物では意図的に起こせません。

代わりに**2種類のモック**を使い分けます。

```
gomock    … インターフェースの偽物を作る
            「CreatePage がエラーを返したら？」を試す
            → UseCase層で使う

httptest  … 偽のHTTPサーバーを立てる
            「401が返ってきたら？」を試す
            → Gateway層（クライアント実装）で使う
```

```
UseCase層          Gateway層              外部
─────────          ─────────              ────
NotionSync   ──▶   NotionClient   ──▶   api.notion.com
             ▲                    ▲
         gomock で              httptest で
         差し替え                差し替え
```

**本物を呼ぶのは、最後に手で確認するときだけ**です（第6章）。

### 「モックのテストが全部通るのに動かない」を防ぐ

各層をモックで固めても、**層のつなぎ目**は検証できません。

```
publish が 200 を返す        … Controller のテストで分かる
公開後に一覧へ出る           … どの層のテストでも分からない
```

今回はCQRSなので、書き込み（publish）と読み出し（一覧）が**別テーブル**です。
コピー処理を1行忘れても全テストが通り、画面にだけ出ません。

そこで**実DBを使い、Notionだけモックにした**テストを置きます。

```
実物 … Echo / Controller / UseCase / sqlc / PostgreSQL
モック … Notion APIのみ
```

使い捨てのDBコンテナを起動して実行するので、CIでも回せます。
**QAケースをそのまま自動化する**形になり、手動確認の回数を減らせます。

### 層ごとの方法と目標

| 層 | 方法 | 検証すること | 目標 |
|---|---|---|---:|
| Domain | 単体テスト | 連携可否の判定 | 90%+ |
| UseCase | gomock | 処理の流れ、呼び出し順序 | 80%+ |
| Gateway (Notion) | httptest | HTTPの扱い、リトライ | 80%+ |
| Controller | httptest | ステータスコード | 80%+ |
| シナリオ | 実DB + Notionモック | 操作をまたいだ状態の整合 | - |
| E2E | 手動 | 本当に繋がるか | - |

目標値は第2章の実測値が根拠です（`domain/service` が100%、`controller` が84.7%）。
**既存を下回らないことが基準**です。

### テストしやすい構造にするための制約

実装前に決めておけば、あとから直さずに済みます。

```
□ Notionクライアントのベースurlを差し替え可能にする
   → NewClient(token, WithBaseURL(url)) の形にする
   → httptest のモックサーバーを差し込むため

□ タイムアウトを外から設定可能にする
   → WithTimeout(d) を用意する

□ 外部APIはインターフェース越しに呼ぶ
   → port.NotionClient として定義する（gomock 用）
```

これらは第5章でAIに渡す指示に、そのまま含めます。

## QAケースを洗い出す

「どう動けば合格か」を、**実装を知らない人でも判定できる形**で書きます。

### 洗い出しの手順

```
1. 正常系のシナリオを書く
2. 第1章のヒアリング結果を確認項目に変換する
3. 第2章の設計判断を確認項目に変換する
4. 異常系の観点リストで網羅する
5. 既存機能が壊れていないことの確認を足す
```

### 正常系

```markdown
### QA-01 公開するとNotionにページができる
前提: テンプレートに親ページURLが設定されている
操作: 下書きのノートを「公開」する
期待: 公開される。Notionの指定ページ配下にページができる
      タイトル・セクションが反映されている
      詳細画面に「Notionで開く」リンクが出る

### QA-02 公開中に編集するとNotionも更新される
操作: 公開中のノートの本文を書き換えて保存する
期待: Notionに新しいページができない（重複しない）
      既存のページの内容が更新されている

### QA-03 非公開に戻すとNotionから消える
操作: 「非公開にする」を押す
期待: /notes から消える。Notionのページがゴミ箱に入る

### QA-04 再公開すると同じページが戻る
操作: QA-03 のあと、もう一度「公開」する
期待: 新しいページができない。URLが変わらない
```

### 要件・設計から変換したもの

| 元になった決定 | QAケース |
|---|---|
| 権限はオーナーのみ | QA-10 他人のノートは公開・非公開にできない |
| 削除時Notionは残す | QA-12 ノートを削除してもNotionのページは残る |
| 親ページはテンプレート単位 | QA-13 別テンプレートのノートは別の親ページ配下に |
| 連携失敗なら公開もしない | QA-20 Notion障害中は公開できず、下書きのまま |
| 同上（非公開時） | QA-21 Notion削除に失敗したら非公開にならない |
| 設定不備で止めない | QA-22 `NOTION_API_KEY` 未設定でもアプリが起動する |
| 既存データの救済 | QA-23 公開済み未連携のノートに手動連携ボタンが出る |

```markdown
### QA-20 Notion障害時は公開できない（ロールバック）
前提: NOTION_API_KEY を無効な値にする（障害を模擬）
操作: 下書きのノートを「公開」する
期待: 公開されない（下書きのまま）。/notes に出ない
      「Notionへの連携に失敗したため公開できませんでした」と表示
      もう一度押せば再試行できる

### QA-22 設定未投入でもアプリが起動する
前提: NOTION_API_KEY を未設定にする
操作: アプリを起動する
期待: 正常に起動する。ノートの作成・編集・閲覧は通常どおり
```

> **QA-20 が今回の設計の核心**
> 第2章②で「ロールバックする」と決めた結果です。
> ここが通らないと、状態がずれる設計になってしまいます。

### 異常系は観点リストで網羅する

思いつきでは漏れます。

```
【ネットワーク】タイムアウト / 接続できない
【HTTPステータス】400 / 401 / 403★ / 404★ / 429★ / 5xx
【レスポンス】JSONが壊れている / 期待したフィールドが無い
【データ】タイトルが空・長すぎる / 本文が巨大（ブロック上限100）★ / 絵文字
【状態】親ページ未設定 / Notion側でページを手動削除★ / 同時に2回リクエスト
【拒否】こちらが入力を弾いたとき、Notionは呼ばれていないか★
```

★ は実際によく起きるもの。QAケースに必ず含めます。

| ID | 内容 | 期待 |
|---|---|---|
| QA-30 | 親ページ未設定のノートを画面で開く | 公開ボタンが非活性。理由が表示される |
| QA-30b | 同じ状態でAPIを直接叩く | エラーが返り、公開されない |
| QA-31 | 共有していないページを指定 ★ | 「Notion側で共有してください」と対処法が出る |
| QA-33 | Notion側でページを手動削除 ★ | エラーにせず新しいページを作る（404でフォールバック） |
| QA-34 | 公開ボタンを高速で2回押す | ページが1つだけできる |
| QA-35 | Notion成功後にDB更新が失敗 | 作られたページがゴミ箱に入る（孤児が残らない） |
| QA-36 | 不正な入力で編集（存在しないセクションID等）★ | エラーが返り、**Notionのページも書き換わらない** |

> **QA-33 は設計の見直しにつながった**
> この観点を洗い出した結果、「404のときは新規作成にフォールバック」という
> 仕様が必要だとわかりました。
> **実装前にQAケースを書くと、仕様の穴が見つかります。**

### 外部APIがあると「失敗」が2方向になる

QA-35 と QA-36 は似ていますが、**失敗する主体が違います**。

```
外部が失敗する … QA-31 / QA-33     「Notionが落ちた」「権限がない」
自分が失敗する … QA-35 / QA-36     「DB更新が落ちた」「入力を弾いた」
```

見落とされやすいのは後者、特に **QA-36（自分が入力を弾いたとき）** です。
「弾いたんだから何も起きないはず」と考えてしまうためです。

しかし**弾く場所が外部API呼び出しより後ろだと、手遅れ**になります。

```
❌ Notionを更新 → 検証 → 不正なので中断 → DBはロールバック
                                          Notionだけ書き換わって食い違う

✅ 検証 → 不正なら即中断（Notionを呼ばない）
        → 正しければ Notionを更新 → DB更新
```

**入力の検証は、外部APIを呼ぶ前に済ませる。** 第2章⑥で
「Notionを先に呼ぶ」と決めましたが、それは**検証を通った後の話**です。

> **この観点は、後から追加されたものです**
> 当初の観点リストに【拒否】はなく、実装レビューで
> 「検証より先にNotionを呼んでいる」と指摘されて発覚しました。
> **観点リストも完璧ではありません。**
> 外部システムを触る機能では「自分が拒否したとき」を必ず入れてください。

### デグレ確認

第2章で `ChangeStatus` と `Update` を変更すると決めたので、
**既存の公開・編集機能そのものがデグレ対象**です。

```
QA-40  ノートの作成・編集・削除が従来どおり動く
QA-41  テンプレートの作成・編集・削除が従来どおり動く
QA-42  一覧・検索が従来どおり動く
```

## エラーメッセージの文言

QAケースを書くと、何を表示するか決める必要が出てきます。

| 状況 | 文言 |
|---|---|
| 親ページ未設定 | 画面:「このテンプレートにNotionの置き場所が未設定です」<br>API: 400 で同内容 |
| 403 | 「Notionページへのアクセス権がありません。Notion側で共有設定を確認してください」 |
| 404 | （新規作成にフォールバックするのでユーザーには見せない） |
| 429 | 「Notionが混み合っています。しばらく待ってから再試行してください」 |
| 5xx / タイムアウト | 「Notionへの接続に失敗しました。再試行してください」 |

> **403の文言はサポートコストに直結します**
> Notion連携で最も多い問い合わせが「連携できない」＝403です。
> 何をすればいいかを文言に含めると、問い合わせが激減します。
