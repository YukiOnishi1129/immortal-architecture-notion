# ④ テスト方針とQAケース

> **この章のゴール**
> 実装に入る前に「どう動けば合格か」を決めておく。
> テストの粒度ごとに、いつ何を作るかを整理する。

---

## なぜ実装前にテストを考えるのか

```
❌ 実装が終わってからテストを考える
   → 「これテストしづらい構造だな…」と気づく
   → リファクタリングが発生
   → または「まあ動いてるしいいか」でテストが薄くなる

✅ 実装前に決めておく
   → テストしやすい構造で実装できる
   → 受け入れ基準が明確なので、完了判定がぶれない
   → AIに実装させるとき、テスト要件も一緒に渡せる
```

もう一つ重要な理由があります。

**QAケースは、仕様が決まった時点で書けます。** 実装を待つ必要がありません。
第2章で設計方針が決まり、第3章で影響範囲がわかった今、**すでに書ける状態**です。

---

## テストの粒度と作るタイミング

テストは一つの工程ではありません。粒度によって作るタイミングが違います。

```
┌──────────────────────────────────────────────────────┐
│ QAケース（受け入れ基準）                                │
│   いつ作る: 設計直後（＝この章）                        │
│   誰が使う: 実装者・レビュアー・QA担当                  │
│   粒度:     「どう動けば合格か」のシナリオ               │
├──────────────────────────────────────────────────────┤
│ ユニットテスト / インテグレーションテスト                │
│   いつ作る: 実装と同時（＝第6章のPRごと）                │
│   誰が使う: 実装者                                     │
│   粒度:     関数・クラス・層の振る舞い                   │
├──────────────────────────────────────────────────────┤
│ リリース判定・監視                                      │
│   いつ作る: リリース直前（＝第7章）                      │
│   誰が使う: リリース担当・運用担当                       │
│   粒度:     システム全体が壊れていないか                 │
└──────────────────────────────────────────────────────┘
```

この章で作るのは**一番上**です。下2つは後の章で扱います。

## テスト方針を決める

### 外部APIは本物を呼ばない

```
❌ テストで本物のNotion APIを呼ぶ

1. Notionが落ちるとテストが落ちる
   → 自分のコードは正しいのにCIが赤くなる

2. 遅い
   → 1回のAPI呼び出しに1秒。テスト100個で100秒

3. レート制限に引っかかる
   → CIが並列実行されると即座に429

4. テストのたびにゴミページができる

5. APIキーをCIに置く必要がある
   → セキュリティリスク

6. 異常系をテストできない
   → 「500が返ってきたとき」を意図的に起こせない
```

**6番目が決定的です。** 異常系こそテストしたいのに、本物では再現できません。

### モックのレベルを層ごとに決める

```
┌────────────────────────────────────────────────┐
│ レベル1: インターフェースをモック（gomock）       │
│   対象: UseCase層                               │
│   検証: 「クライアントが成功/失敗を返したら？」    │
├────────────────────────────────────────────────┤
│ レベル2: HTTPサーバーをモック（httptest）        │
│   対象: Gateway層（クライアント実装）             │
│   検証: 「HTTPで401が返ってきたら？」            │
├────────────────────────────────────────────────┤
│ レベル3: 本物を使う（手動）                      │
│   対象: 実装中の動作確認とリリース前の最終確認     │
│   検証: 「本当にNotionにページができるか」        │
└────────────────────────────────────────────────┘
```

### 層ごとの目標

| 層 | テスト方法 | 何を検証するか | 目標カバレッジ |
|---|---|---|---:|
| **Domain** | 純粋な単体テスト | 連携可否の判定、状態遷移 | 90%+ |
| **UseCase** | gomock | 処理の流れ、呼び出し順序 | 80%+ |
| **Gateway (Notion)** | httptest | HTTPの扱い、リトライ | 80%+ |
| **Gateway (DB)** | sqlmock | SQLの正しさ | 70%+ |
| **Controller** | httptest | ステータスコード、レスポンス形式 | 80%+ |
| **E2E** | 手動 | 本当に繋がるか | - |

#### 目標値の根拠

第3章で実測した既存のカバレッジがあります。**これを下回らないことが基準**です。

```
domain/service           100.0%  ← 新しいdomainもこの水準を目指す
domain/template           97.4%
driver/config             95.2%
domain/account            92.6%
domain/note               86.3%
adapter/http/controller   84.7%  ← 新しいcontrollerもこの水準
adapter/http/presenter    50.9%
usecase                   37.2%  ← 既存の課題
```

> **usecase の 37.2% について**
> `NoteCommandInteractor` にテストがないためです（第3章参照）。
> 新しく書く `NotionSyncInteractor` は80%以上にして、全体を押し上げます。

### テストしやすい構造にするための制約

実装前に決めておくことで、あとから直さずに済みます。

```
□ Notionクライアントのベースurlを差し替え可能にする
   → httptest のモックサーバーを差し込むため
   → NewClient(token, WithBaseURL(url)) の形にする

□ タイムアウトを外から設定可能にする
   → タイムアウトのテストを書くため
   → WithTimeout(d) を用意する

□ 外部APIはインターフェース越しに呼ぶ
   → UseCase層で gomock を使うため
   → port.NotionClient として定義する

□ 時刻を直接取らない（必要なら注入する）
   → last_synced_at の検証を安定させるため
```

> これらは第6章（実装）でAIに渡す指示に、そのまま含めます。

## QAケースを洗い出す

「どう動けば合格か」を、**実装を知らない人でも判定できる形**で書きます。

### 洗い出しの手順

```
1. 正常系のシナリオを書く（ハッピーパス）
2. 第1章のヒアリング結果を、1つずつ確認項目に変換する
3. 第2章の設計判断を、確認項目に変換する
4. 異常系の観点リストで網羅する
5. 既存機能が壊れていないことの確認を足す
```

### 1. 正常系

```markdown
### QA-01 公開するとNotionにページができる
前提: テンプレートに送り先が設定されている
操作: 下書きのノートを「公開」する
期待: 公開される（/notes に出る）
      Notionの指定ページ配下に新しいページができる
      タイトル・セクションが反映されている
      詳細画面に「Notionで開く」リンクが出る

### QA-02 公開中に編集するとNotionも更新される
前提: QA-01 が完了している
操作: ノートの本文を書き換えて保存する
期待: Notionに新しいページができない（重複しない）
      既存のページの内容が更新されている

### QA-03 非公開に戻すとNotionから消える
前提: QA-01 が完了している
操作: 「非公開にする」を押す
期待: /notes から消える
      Notionのページがゴミ箱に入る（見えなくなる）

### QA-04 再公開すると同じページが戻る
前提: QA-03 が完了している
操作: もう一度「公開」する
期待: Notionに新しいページができない
      ゴミ箱から同じページが戻る（URLが変わらない）
```

### 2. ヒアリング結果からの変換

第1章で決めた要件を、そのまま確認項目にします。

| ヒアリング結果 | QAケース |
|---|---|
| 権限はオーナーのみ | QA-10 他人のノートは公開・非公開にできない |
| 更新に追従する | QA-02（上記） |
| 削除時Notionは残す | QA-12 ノートを削除してもNotionのページは残る |
| 送り先はテンプレート単位 | QA-13 別テンプレートのノートは別ページ配下に作られる |

### 3. 設計判断からの変換

第2章の決定事項が守られているかも、確認項目になります。

| 設計判断 | QAケース |
|---|---|
| 連携失敗なら公開もしない | QA-20 Notion障害中は公開できず、ノートは下書きのまま |
| 同上（非公開時） | QA-21 Notion削除に失敗したら非公開にならない |
| 設定不備で止めない | QA-22 NOTION_API_KEY 未設定でもアプリが起動する |
| 既存データの救済 | QA-23 公開済み未連携のノートに手動連携ボタンが出る |

```markdown
### QA-20 Notion障害時は公開できない（ロールバック）
前提: NOTION_API_KEY を無効な値にする（障害を模擬）
操作: 下書きのノートを「公開」する
期待: 公開されない（下書きのまま）
      /notes に出ない
      「Notionへの連携に失敗したため公開できませんでした」と表示
      もう一度押せば再試行できる

### QA-21 Notion削除失敗時は非公開にならない
前提: 公開済みノート。Notionのページを事前に手動削除しておく
操作: 「非公開にする」を押す
期待: 公開のまま（/notes に残る）
      エラーメッセージが表示される

### QA-22 設定未投入でもアプリが起動する
前提: NOTION_API_KEY を未設定にする
操作: アプリを起動する
期待: 正常に起動する
      ノートの作成・編集・閲覧は通常どおり動く
      公開しようとすると「Notion連携が設定されていません」

### QA-23 既存の公開済みノートを手動連携できる
前提: 機能リリース前から公開されていたノート
期待: 詳細ページに「Notionに未連携です [連携する]」が出る
操作: 押す
期待: Notionにページができ、以降は自動同期される
```

> **QA-20 が今回の設計の核心**
> 第2章の論点A-2で「ロールバックする」と決めた結果です。
> ここが通らないと、**状態がずれる設計**になってしまいます。

### 4. 異常系の観点リスト

異常系は思いつきでは網羅できません。観点から機械的に出します。

```
【ネットワーク】
□ タイムアウト
□ 接続できない（DNS解決失敗、接続拒否）

【HTTPステータス】
□ 400 リクエストが不正
□ 401 トークンが無効・失効
□ 403 権限がない（ページが共有されていない）★
□ 404 親ページが存在しない・削除された ★
□ 429 レート制限 ★
□ 500/502/503 相手のサーバーエラー

【レスポンス内容】
□ JSONが壊れている
□ 期待したフィールドがない

【データ起因】
□ タイトルが空
□ タイトルが長すぎる（Notionの制限: 2000文字）
□ 本文が巨大（1リクエストのブロック数上限: 100）★
□ 絵文字・特殊文字・改行を含む
□ セクションが0個

【状態起因】
□ 送り先が未設定
□ Notion側でページが手動削除された ★
□ 同時に2回リクエストが来る
```

★ は実際によく起きるものです。QAケースに必ず含めます。

| ID | 内容 | 期待 |
|---|---|---|
| QA-30 | 送り先未設定のテンプレートで公開 | 公開されず「テンプレートにNotionの送り先が設定されていません」と出る |
| QA-31 | 共有していないページを指定 ★ | 「Notion側で共有してください」と対処法が出る |
| QA-32 | 失敗後の再試行 | 「再試行」ボタンが出て、押すと再実行される |
| QA-33 | Notion側でページを手動削除 ★ | エラーにせず新しいページを作る（404でフォールバック） |
| QA-34 | 連携ボタンを高速で2回押す | ページが1つだけできる（ボタンが無効化される） |

> **QA-33 は設計の見直しにつながった**
> この観点を洗い出した結果、「404のときは新規作成にフォールバック」という
> 仕様が必要だとわかりました。
> **実装前にQAケースを書くと、仕様の穴が見つかります。**

### 5. デグレしていないことの確認

第3章で「変更しない」と決めたものが、本当に無事かを確認します。

```markdown
### QA-40 既存のノート機能が動く
前提: 送り先が設定済みのテンプレートで作ったノート
操作: 作成・編集・削除を一通り行う
期待: すべて従来どおり動作する
      （下書きのうちはNotion連携が走らない）

### QA-41 既存のテンプレート機能が動く
操作: テンプレートの作成・編集・削除を行う
期待: すべて従来どおり動作する
      作成時に送り先の選択が必須になっている

### QA-42 一覧・検索が動く
操作: ノート一覧、マイノート、検索を使う
期待: 従来どおり表示される
```

## エラーメッセージの設計

QAケースを書くと、**エラー時に何を表示するか**を決める必要が出てきます。
これも実装前に決めておきます。

```go
// ❌ ユーザーが何をすればいいかわからない
return errors.New("notion api error: 403")

// ✅ 次の行動がわかる
return fmt.Errorf(
    "Notionページへのアクセス権がありません。" +
    "Notion側で対象ページをインテグレーションに共有してください: %w", err)
```

| 状況 | 表示する文言 |
|---|---|
| 送り先未設定 | 「テンプレートにNotionの送り先が設定されていません」 |
| 403 | 「Notionページへのアクセス権がありません。Notion側で共有設定を確認してください」 |
| 404 | （新規作成にフォールバックするのでユーザーには見せない） |
| 429 | 「Notionが混み合っています。しばらく待ってから再試行してください」 |
| 5xx / タイムアウト | 「Notionへの接続に失敗しました。再試行してください」 |
| APIキー未設定 | 「Notion連携が有効になっていません」（管理者向け） |

> **403の文言はサポートコストに直結します**
> Notion連携で最も多い問い合わせが「連携できない」＝403です。
> 何をすればいいかを文言に含めておくと、問い合わせが激減します。

## この章の成果物の使い道

```
QAケース
   │
   ├─→ 第5章: PRの受け入れ基準になる
   │        「PR⑤の完了条件 = QA-01, QA-22 が通ること」
   │
   ├─→ 第6章: AIへの指示に含める
   │        「QA-33 のフォールバックを実装して」
   │
   └─→ 第7章: リリース判定の材料になる
            「全QAケースが通ったのでリリース可」
```

**この章で決めたことが、以降すべての工程の基準になります。**

## この章のチェックリスト

```
□ 外部APIをテストで呼ばない方針を決めたか
□ 層ごとのテスト方法と目標カバレッジを決めたか
□ 既存のカバレッジを下回らない基準にしたか
□ テストしやすい構造にするための制約を書き出したか
□ 正常系のQAケースを書いたか
□ ヒアリング結果を確認項目に変換したか
□ 設計判断が守られているかの確認項目を入れたか
□ 異常系を観点リストで網羅したか
□ デグレ確認の項目を入れたか
□ エラーメッセージの文言を決めたか
```
